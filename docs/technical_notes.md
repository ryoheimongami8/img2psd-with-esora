# lineart2psd

画像を入力して、線画抽出・AI生成・レイヤーPSD書き出しまでを自動で行うツール

![処理フロー](docs/pipeline_overview.png)

## 処理の流れ
1. 入力画像を 2048×2048 にパディング（歪みなし）
2. 透過線画SVGを抽出
3. Gemini (`gemini-3.1-flash-image`) で画像生成（API要）
4. （任意）キー背景版をもう一度生成し、そこから背景透過マスクを作ってフリンジを微調整
5. 元画像（不透明）・切り抜き・生成画像・線画・マスクの5レイヤーでPSDを出力

`mask` レイヤーはレイヤーレコードのフラグ bit 1 で非表示にして書き出す。参照用に
同梱するが、不透明なグレースケール板がスタックの一番上にあると開いた人はそれしか
見えないため。フラット化プレビューも非表示レイヤーを飛ばして合成する。

## 背景透過

「背景透過」を有効にすると、②とは**別に**もう一度 Gemini を呼び、①でパディングした元画像の
背景だけをキー色に置き換えた画像を生成します。この画像は**マスクを作るためだけ**に使い、
出力の色は必ず元画像（と②の生成画像）から取ります。

生成を1回にまとめてキー背景版から色も取る作り方は、実運用で破綻しました。モデルは細い髪を
「髪の色」ではなく「暗くしたキー色」として描くことがあり（実測例 `[0,90,0]`）、
そういう画素には復元すべき前景色がそもそも存在しないため、輪郭に沿ってキー色の縁が残ります。

マスクは距離キーではなく**既知背景マッティング**で求めます。背景色 `K` が既知なので
`C = αF + (1−α)K` を α について解け、アンチエイリアスされた境界画素の α を逆算できます。
前景色 `F` は最近傍の「確実に前景」な画素から伝播させ、再構成誤差が大きい画素だけ
距離キーへ退避します。

キー色の判定は **CbCr 距離と正規化色度距離の両方**で行います。CbCr 距離は彩度の大きさに
比例するので、暗くされたキー色を「キー色から遠い＝前景」と誤判定します。色度距離は輝度に
不変なのでこれを捕まえられます。実測の分離は明瞭で、平坦背景 p95 0.019 / 正当な半透明画素
p1 0.499 / 確実な被写体 p1 0.694 でした。

- **キー色**: green / magenta / blue。キャラクターに使われていない色を選んでください
- **キー色リム除去**（既定 0.35, 0 で無効）: 「不透明と判定されたのに色相はキー色そのもの」
  という画素を背景に戻します。実測で輪郭沿いのキー色画素が 2,359 → 21 px（−99%）になり、
  不透明面積の減少は 0.6〜3.8%（＝膨らんでいた縁そのもの）。ベンチマークへの影響はありません
  （`alpha_mae_edge` はむしろ 14.72→14.54 / 15.70→15.28 と微改善）。
  キャラクターがキー色の服を着ている場合だけ下げてください
- **境界の処理**（既定 `matting`）: キー背景版と元画像は 1px 程度しか一致しません。
  実測した細い髪では、キーマスクは髪の両側の**純白の背景画素**に α 0.43 / 0.71 を与え、
  その間の暗い芯に 0.00 を与えていました。そこでキーマスクを **trimap**（確実な前景 /
  確実な背景 / 不明）に降格させ、不明領域の α を**元画像に対して**解き直し（PyMatting の
  Closed-Form Matting）、続いて**前景色推定**（Multi-Level）で境界に混ざった背景色を分離します。

  3つのモードを比較できます。

  | モード | 処理 | 実データ（消えた髪候補 / 髪領域の平均α） |
  |---|---|---|
  | `analytic` | 旧・解析的（min を取るだけ） | 3113 / 0.709 |
  | `foreground` | キーの α ＋ 前景色推定 | 2875 / 0.730 |
  | **`matting`** | **α 再推定 ＋ 前景色推定** | **1341 / 0.849** |

  `analytic` と `foreground` は α を減らせても**増やせない**ので、キー側が消した髪を
  復元できません。`matting` だけが復元できます。

  **α 再推定はキーマスクが間違っている所にだけ適用します。** ベンチマークは正解 α を持つので
  ここは実測で決めました: キー画像が厳密な合成である場合、キーの α は不明領域で既に非常に良く
  （MAE 5.9/255）、元画像から解き直すと 18.0 に悪化します（白地に密な暗い髪は、平坦な緑キーより
  難しい問題です）。一方キー画像を人工的にずらすと順序が逆転し、ずれ 0 / 0.5 / 1.0 / 1.5px に対して
  キーの α は 14.3 / 26.0 / 42.7 / 55.5 と悪化するのに、解き直した α は約 33.5 で**平坦**でした。
  そこで既定ではキーの α を採用し、**両画像が実際に食い違っている近傍でだけ**解き直した α に
  置き換えます。ベンチマークでの代償は alpha_mae_edge +0.26、ずれ 1px では −4.0 の改善です。

  trimap の閾値も実測で決めています。背景は `α≤8`（`==0` ではありません。キーマットは背景全体に
  α 1〜4/255 の微小ノイズを持つため、`==0` だと背景が 44% しか取れません）。
  「キーが残した白フチ」の判定は**キー側の背景に接している画素に限定**します。これを入れないと、
  ベンチマークの明るい服の内部 35,335px（正解 α は 0.999、つまり完全な前景）が不明領域に落ちて、
  そこに穴が開きます。この条件を入れると 60px まで下がります

- **trimap の不明バンド幅**: 既定 3px。実測で FG 24.2% / BG 70.3% / 不明 5.5% になり、
  計測した誤り候補（消えた髪・白フチ）が **100% 不明領域に入り**、
  白い衣装の内部 187,487px は **100% 確実前景に残ります**

- **不明帯の扱い**（`matting` 使用時のみ・既定「不明帯全体を再推定」）: 不明領域の α を
  最終的にどちらから取るかの選択です。

  | モード | 挙動 | 実データ: 髪の隙間に残る白背景（α&gt;128 / α&gt;64） | 被写体を削る量 |
  |---|---|---|---|
  | **不明帯全体を再推定**（既定） | 不一致の有無に関わらず、不明帯は常に解き直した α を採用 | **5px / 63px** | 約900px（図の0.09%、細い毛先） |
  | 不一致のみ再推定 | 元のキー α と解き直した α が実際に食い違う近傍だけ置き換え、それ以外はキー α を維持 | 204px / 905px | 少ない |

  ベンチマーク（正解 α あり）は「不一致のみ」を支持しますが、これはベンチマークのキー画像が
  元画像との**完全な合成**で作られているためです。実際の2回のGemini生成では髪が描き直されて
  シルエットごと変わるため、この失敗モードをベンチマークは再現できません。実画像では
  「不明帯全体を再推定」が隙間の白残りを大きく減らすため既定にしていますが、
  毛先が痩せて見える場合は「不一致のみ」に切り替えてください。

  どちらのモードでも、髪の隙間の**中心1点**は別経路で保護されます（`pin_background`）。
  キー画像自身が背景と判定し、かつ元画像も局所または全体の背景色と一致する画素だけを
  背景として固定し、縁は不明帯に残して解かせます。位置ずれで動いた髪筋は元画像側の
  色チェックに落ちるため、誤って透明化されません。

- **色の保持範囲は α ではなく距離で決めています。** α が高い輪郭画素にも白の混ざった元RGBが
  戻ってしまうため、確実前景の内側 3〜6px で滑らかに元画像の色へ切り替えます。
  完全内部の RGB は元画像と差 0 です

- **マスクの作り方**: 既定は `soft`。`binary` は α 0.5 の画素を完全不透明に丸めるため、
  元画像の背景色が 1px そのまま出ます
- **超解像バックエンド**: 既定は Lanczos。Real-ESRGAN も選べますが、ベンチマーク実測では
  マット精度が約 2 倍悪く（alpha_mae_edge 19.2 vs 36.4）約 7 倍遅くなります。ESRGAN は
  エッジを描き直すため、マッティングが必要とする前景と背景の混合比を壊します
- **超解像倍率**: 2 で十分（1 より良く、4 と同等）
- **フリンジ調整**: スライダーを離すと即座に再計算されます（数百 ms）。形状だけを動かし、
  **前景色は再推定しません**。そのため choke を動かしても色は変化しません（実測 RGB 差 0）。
  choke は整数半径の膨張/収縮を端数で線形補間するため、`±0.01` のようなごく小さい値でも
  薄く細い毛先が消えません（以前は α を二値化してから距離場を作っていたため、
  非0の choke で即座に消えていました）
- **エッジ色浄化**: 元画像の背景色を境界画素から差し引きます。背景色はキー色ではなく、
  マスクが「背景」と言う位置の**元画像側の色**を局所推定したものを使うので、元画像の背景が
  一様でなくても機能します。背景色が定まらない領域では補正を行いません

キー背景版は元画像と位置が一致している必要があります。ずれを検出した場合はログに警告が出るので、
④-a をやり直してください（実測では 0px ずれ、シルエット IoU 0.91）。

Real-ESRGAN を使う場合のみ追加インストールが必要です。未導入なら自動的に Lanczos に
フォールバックするので、本体の動作には影響しません。

```bash
pip install -r requirements-sr.txt
```

重みは初回使用時に `models/` へ自動ダウンロードされます（約 18MB, BSD-3-Clause）。
ネットワークが使えない場合は手動で配置してください。

## 生成画像の位置合わせ

モデルは絵を塗り直すのではなく描き直すので、返ってくる画像は構図こそ同じでも
フレーミングが数％ずれる。実測（GPT Image 2 / 2048px 正方形）で **スケール 2.2%、
縦 12px** のずれがあった。線画も切り抜きも `square` から作られるため互いには
ぴったり合っており、**ずれるのは生成レイヤーだけ**。PSD では全輪郭が二重に見える。

`core/align.py` がこれを相似変換（拡大縮小＋平行移動）として測って戻す。

- 照合は**色ではなく勾配強度**で行う。元画像は線画や写真、生成画像は塗り済みで、
  両者が確実に共有しているのはエッジの形だけだから
- スケールを 0.90〜1.10 で走査し、各スケールでの残りのずれは**位相相関**が一度に出す。
  3次元の総当たりにせずに済む
- 探索は長辺 512px で行う。パラメータが3つしかない変換に全解像度は要らない
- 相関が `MIN_GAIN`（0.02）以上改善しなければ**何もしない**。すでに正しく
  フレーミングされた画像をノイズで動かさないため

実測（上と同じ画像）でエッジ相関 **0.31 → 0.70**。残差はモデルが実際に描き変えた
部分（毛皮の房、コート内側の線）で、これはどんな変換でも合わせられない。

キー背景画像には適用していない。マスクは trimap を経由して**元画像に対して**
α を解き直すので、既に元画像の座標系に乗っている（「背景透過」の節を参照）。

## マスク品質の検証

`benchmark/` に正解 α と正解前景色つきのテストデータがあります。

```bash
python tools/eval_matte.py --crops A,B,C,D
python tools/eval_matte.py --two-pass --methods analytic,foreground,matting --shift 0,0.5,1.0,1.5
```

`--two-pass` は実運用と同じ構成（マスクはキー画像から、色は別の画像から）を評価します。
`white_reference` はキー画像と同じ F・α から作られているので元画像の代役になり、
実データと違って正解 α と正解前景色の両方があります。`--shift` はキー画像を故意にずらして、
2回の生成がずれるという実データ側の失敗をベンチマーク上で再現します。

完全前景と完全背景で全画素の 95% を占めるため、指標はすべて境界画素に限定しています。
`distance`（ベースライン）→ `pipeline`（実装）→ `oracle`（正解 F を与えた上限）の
3 点を出すので、改善が数式由来か F 伝播由来かを切り分けられます。

`rim_px`（前景と判定されたのに色相はキー色、という画素数）はベンチマークでは常に 0 です。
この失敗はベンチマークに存在しません — ベンチマークは平坦な `#00FF00` への線形合成で
**構築されている**ため、境界画素は必ず F↔K の線分上に乗るからです。実データ専用の指標です。

`test_data/` には実際の生成画像（`*_gb.png` がキー背景版）があります。正解 α が無いので
MAE は使えず、代わりに「エッジの色が内部の色と連続しているか」「完全不透明部の色が
変化していないか」「`rim_px` が十分小さいか」で確認します。

### 既知の限界
生成画像では、被写体の内部にごく淡い半透明が残ることがあります（背景の透け量は平均 3/255
程度、内部画素の 0.07〜0.28% が半透明を下回る）。`F` を画素自身ではなく近傍の確実前景から
推定していることに由来します。`speck_repair_area` で一部は埋められますが、効果は限定的
（0.283% → 0.259%）でベンチマークのエッジ精度を落とすため既定では無効です。

実際の生成画像では、境界画素の 6 割前後で再構成誤差ガードが働き距離キーへ退避します
（今回のテスト画像で 67%、この修正の前から 62%）。Gemini が描くエッジが `C = αF + (1−α)K`
の線分上に乗っていないためで、マッティングの精度上限はここで決まっています。
ベンチマーク（線分上に乗るよう構築されている）では 0.6〜3.8% です。

## 参照プロンプト
画像のキャラクターを忠実に維持して、線画を消して、色塗だけの画像を出力してください。つまり黒い線を消して、色だけのキャラクターを出力してください。線画なし、輪郭線なし、境界線なし、参照カラー画像のカラーパレットを厳密に維持、元の陰影スタイルを維持、細部を再解釈しない、再設計しない、参照カラー画像の絶対的な忠実さで出力し、線画削除以外のいかなる細部も再解釈、再設計、再スタイル化しないでください。

## セットアップ

Windows なら `setup.bat` をダブルクリックするだけです（`.venv` の作成と依存関係の
インストールを行います）。手動で行う場合:

```bash
python -m venv .venv
.venv\Scripts\activate      # Windows
pip install -r requirements.txt
```

画像生成には Esora CLI が必要です。未インストールなら:

```bash
uv tool install "D:\40_Esora\01_CLI\esora_api_cli-0.4.5-py3-none-any.whl"
```

## 起動

`run.bat` をダブルクリックします。サインインが切れていれば自動で
`esora-api auth login` を実行し、その後アプリを起動します。
ポートが埋まっている場合は引数で変えられます（例: `run.bat 7870`）。

手動で起動する場合:

```bash
python app.py
```

ブラウザで `http://127.0.0.1:7860` が自動で開きます。新UIが `/`、
従来の Gradio UI が `/gradio` です。

## 認証（Esora）

APIキーはありません。Esora は業務用 Google アカウントのブラウザサインインで認証します。

```bash
esora-api auth login
```

ID トークンは `~/.config/esora/token-default.json`、リフレッシュトークンは Windows
資格情報マネージャー（サービス名 `esora-api-cli`）に CLI が保存します。アプリはそれを
読むだけで、期限が近づいたら CLI を呼び直して更新します。認証の実装が一箇所にしか
ないので、**CLI でサインアウトすればアプリも即座に使えなくなります**。

サインインは最大 24 時間で切れます。切れていれば `run.bat` が再サインインを促します。

## モデル

新UIの「詳細設定」、または Gradio UI の「Esora モデル」で選べます。既定は
`gemini_nanobanana_2`。一覧は `esora-api model list` で確認できます。
アスペクト比 `1:1` / サイズ `2K` はパイプラインが 2048px 前提のため固定です。
